# UU Campus TLS Fix · macOS

一个用于排查、缓解特定网络下 **UU 远程 TCP/TLS 连接异常** 的本机适配器。

> **状态：实验性、单机验证，不保证所有校园网或 UU 版本可用。**
> **当前推荐方式：UU 内停用手动代理，通过 Clash 系统代理和规则接入本机修复程序。**
> 2026-11-09 停用 UU 手动 SOCKS5 并重启用户进程后，用户确认仍可连接。
> 这是当前设备与网络的对照结果，不代表所有 UU 版本均无需应用内代理。
> 完整功能、UDP/P2P、文件传输和长期稳定性仍未逐项验证。
> HTTP 200/404 和 TLS 握手成功都不等于完整远控测试通过。

## 解决什么问题

本案例中，同一设备切换手机热点可以连接 UU，校园网下部分接口 TCP 能建立但普通 TLS 握手超时。
保持原域名、开启证书校验，改变首个 ClientHello 的 TLS record 划分后，部分接口可以完成握手。
这支持“网络路径对握手内容或分段敏感”的判断，但不能单凭此确定具体过滤设备或责任方。

修复还处理了两类问题：

- 原本过窄的本机代理白名单误拒绝 UU 自己使用的辅助域名。
- 部分系统 DNS 解析出的信令/中继端点无法完成 TLS；备用端点在原域名、证书校验开启时通过测试。

## 工作方式

```text
UU（手动代理停用）
  → macOS 系统代理 → Clash/Mihomo（本机端口，例如 127.0.0.1:7890）
      ├─ 匹配 UU nrd 域名 → 本机修复程序 127.0.0.1:17899 → UU 服务端
      └─ 其他请求 → 原有规则（本案例校园网使用 DIRECT）
```

**不需要在 UU 内填写 SOCKS5 地址或端口。**
Clash 到本机修复程序的内部连接仍使用 SOCKS5，所以下方示例中的 `type: socks5`
必须保留；这与“在 UU 设置里启用手动 SOCKS5”是两回事。
修复程序把首个 TLS ClientHello 重新划分为 TLS records，再转发到服务端。
这里描述的是匹配规则的连接路径，不意味着全部远控画面或 UDP/P2P 流量都经过本程序。

- 不解密 TLS、不安装 CA、不关闭客户端证书校验。
- 不连接远端 VPN/代理节点；备用 IP 是目标服务端端点，不是中转 VPN。
- 仅监听 IPv4 loopback，不对局域网提供代理。
- 仅允许 `.nrd.nie.163.com` 及两个明确辅助域名的 TCP 443。
- IP 形式的 CONNECT 必须先提供白名单内的 TLS SNI；程序随后按获准域名选择目标，
  不会任意转发到请求中提供的 IP。
- 不修改系统 DNS、hosts、Clash 配置、UU 配置或开机项。
- **不是流量隐身工具，也不保证符合所在网络的管理要求或不被识别。**

## 环境与启动

需求：Python 3.10+ 标准库，无额外依赖。macOS 是本案例平台；代码未在其他平台验证。
开发时使用 Python 3.14；2026-11-09 首次 GitHub Actions 运行中，
macOS / Python 3.10 与 3.14 均通过 17 项离线测试。后续提交请以 Actions 的实际结果为准，
测试不覆盖真实校园网、UU 账号或完整远控功能。

```bash
python3 --version
python3 -m unittest discover -s tests -v
python3 uu_local_proxy.py
```

看到 `LISTEN 127.0.0.1:17899` 后，保持该终端运行；`Ctrl+C` 停止。
如果端口已被先前修复程序占用，**不要重复启动**，也不要随意结束未知进程。
程序不自启，关闭终端、重启或休眠恢复后都需要检查运行状态。

### 使用方式：UU 不启用手动代理，Clash/Mihomo 精确分流

参见 [示例配置](examples/clash-rules.yaml)。

1. 启动本机修复程序，确认 `127.0.0.1:17899` 正在监听。
2. 先备份 Clash 配置，再把示例的本地出站和 UU 域名规则合并到原配置。
   把 UU 规则放在现有兜底规则之前；通过客户端支持的覆写/增强机制持久化，
   避免订阅更新覆盖它，具体操作取决于客户端。
3. 开启 Clash 的 **系统代理**，使用 **规则模式**。
   直连模式会跳过该规则；全局模式可能使用选中的远端节点。
4. 在 UU → 设置 → 网络里，**停用手动代理**。
   如果此前填写过 `127.0.0.1:17899`，点“停用”即可，不必删除留存的地址和端口。
5. 在没有正在进行的远控会话时，退出并重新打开 UU，避免旧连接影响判断；
   检查实际连接，不要只看缓存设备列表。

**不要把 macOS 系统代理端口设成 `17899`。** 系统代理仍由 Clash 接收（例如 `7890`），
`17899` 仅供 Clash 的 UU 本地出站使用。
此程序不是完整 SOCKS5 代理：不支持 UDP ASSOCIATE、DNS 53、任意 TCP 端口或任意网站。
早期在 UU 内启用手动代理时，确实观察到不支持的端口请求被拒绝；因此不再把这种接法
作为默认使用说明。不要为了消除 REJECT 日志而取消白名单限制。

示例不会添加 `MATCH,DIRECT`，以免覆盖你原有的其他软件路由。
原始排障阶段曾临时添加 `MATCH,DIRECT` 以保持校园网下非 UU 流量直连：
这会让其后的原有分流规则不可达，**不是适合直接分发给所有人的默认配置**。
回到必须依赖远端代理的个人网络时，务必恢复自己的路由策略。
系统代理未覆盖的 UU socket 仍不一定会经过 Clash；这次对照只证明本案例停用手动代理后
用户仍能连接。若其他设备/网络不通，应先检查实际路由，不要把此结论当成通用保证。

### 为什么代码和配置里仍出现 SOCKS5？

删掉的是 **UU 应用内手动代理这一步**，不是本地程序的接入协议。
Clash 仍通过 `type: socks5` 把匹配连接交给修复程序；Python 代码和相应测试必须保留。
不能把示例出站改成 `DIRECT`，否则会绕过修复程序。

## 验证

先检查客户端是否恢复服务连接，再实际连接自己拥有或获授权的设备：

1. 顶部服务器连接错误消失。
2. 在线设备状态刷新，而非仅看到缓存设备列表。
3. 能进入远程画面并进行正常操作。
4. 根据需要分别测试文件传输、断线重连、休眠恢复。

可选的基础测试（系统需有 curl；把 `7890` 改成自己 Clash 的 HTTP/mixed 端口）：

```bash
curl --noproxy '' --proxy http://127.0.0.1:7890 \
  --connect-timeout 5 --max-time 10 -o /dev/null \
  -w 'HTTP=%{http_code} TLS=%{time_appconnect}\n' \
  https://api.nrd.nie.163.com/
```

根路径返回 404 也可证明完成了该次 TLS/HTTP 交互，但**不证明业务正常**。
同时检查 Clash 连接详情或本地程序日志，确认该请求确实命中 `UU-Local-TLS-Fix`，
否则单看 HTTP 响应不能证明规则已生效。不要使用 `-k` 跳过证书验证。

## 已知限制

详见 [验证记录与限制](docs/VALIDATION.md)。

- 默认端点映射只反映 2026-11-09 的单次排障，可能失效，不提供自动更新或自动切换。
- 改变 TLS record 并非对所有过滤方式有效；不支持跨多个 record 的 ClientHello 重组。
- TCP only，缺少 UDP、其他端口、IPv6 上游、HTTP 明文升级支持。
- 默认最多同时处理 48 个连接；长连接占满时其他请求可能等待。
- 本地无身份认证，其他本机进程/用户可以访问该端口，不适合不可信多用户主机。
- 只修复了连接路径，不修复 UU 账号、设备离线、服务端权限或 NAT 等其他问题。
- 不应把“当前可用”理解成“没有其他问题”或“可以无人值守长期使用”。

## 撤销

先删除自己添加的 Clash 出站与对应域名规则、重新加载并确认路由已恢复，再停止本程序。
UU 内保持手动代理停用；若早期排障仍启用了它，也应先停用再关闭程序。
不要先停程序却让 Clash 或 UU 继续指向这个端口。
不要覆盖与本项目无关的 DNS 修复、订阅、系统代理或其他分流规则。

此发布版没有安装器和自启项，也不会自动改写本机文件；本次实际排障留下的
本机专用管理脚本、备份和配置状态**不在这个仓库里**。
