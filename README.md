# UU Campus TLS Fix · macOS

一个用于排查、缓解特定网络下 **UU 远程 TCP/TLS 连接异常** 的本机适配器。

> **状态：实验性、单机验证，不保证所有校园网或 UU 版本可用。**
> 2026-11-09 的修复过程中，用户反馈 UU 恢复可用；维护者尚未独立验证完整的远控操作、
> UDP/P2P、文件传输或长期稳定性。HTTP 200/404 和 TLS 握手成功都不等于完整远控测试通过。

## 解决什么问题

本案例中，同一设备切换手机热点可以连接 UU，校园网下部分接口 TCP 能建立但普通 TLS 握手超时。
保持原域名、开启证书校验，改变首个 ClientHello 的 TLS record 划分后，部分接口可以完成握手。
这支持“网络路径对握手内容或分段敏感”的判断，但不能单凭此确定具体过滤设备或责任方。

修复还处理了两类问题：

- 原本过窄的本机代理白名单误拒绝 UU 自己使用的辅助域名。
- 部分系统 DNS 解析出的信令/中继端点无法完成 TLS；备用端点在原域名、证书校验开启时通过测试。

## 工作方式

```text
UU → 本机 SOCKS5 / HTTP CONNECT（127.0.0.1:17899）
   → 重新划分首个 TLS ClientHello record
   → UU 服务端
```

- 不解密 TLS、不安装 CA、不关闭客户端证书校验。
- 不连接远端 VPN/代理节点；备用 IP 是目标服务端端点，不是中转 VPN。
- 仅监听 IPv4 loopback，不对局域网提供代理。
- 仅允许 `.nrd.nie.163.com` 及两个明确辅助域名的 TCP 443。
- IP 形式的 CONNECT 必须先提供白名单内的 TLS SNI；程序随后按获准域名选择目标，
  不会任意转发到请求中提供的 IP。
- 不修改系统 DNS、hosts、Clash 配置、UU 配置或开机项。
- **不是流量隐身工具，也不保证符合所在网络的管理要求或不被识别。**

需求：Python 3.10+ 标准库，无额外依赖。macOS 是本案例平台；代码未在其他平台验证。
开发时使用 Python 3.14；2026-11-09 首次 GitHub Actions 运行中，
macOS / Python 3.10 与 3.14 均通过 17 项离线测试。后续提交请以 Actions 的实际结果为准，
测试不覆盖真实校园网、UU 账号或完整远控功能。

```bash
python3 --version
python3 -m unittest discover -s tests -v
python3 uu_local_proxy.py
```

看到 `LISTEN 127.0.0.1:17899` 后，保持该终端运行；`Ctrl+C` 停止。
如果端口已被先前修复程序占用，**不要重复启动**，也不要随意结束未知进程。
程序不自启，关闭终端、重启或休眠恢复后都需要检查运行状态。

### 接入方式 A：UU 自身的代理设置

在 UU 支持的网络设置中选择手动 SOCKS5：

| 项目 | 值 |
|---|---|
| 地址 | `127.0.0.1` |
| 端口 | `17899` |
| 用户名 / 密码 | 留空 |

**重要限制：此适配器不是完整 SOCKS5 代理。** 它不支持 UDP ASSOCIATE、DNS 53、
任意 TCP 端口或任意网站。UU 可能把其他请求也送到手动代理，这些请求会被拒绝；
可能影响 P2P、直连性能、发现或部分功能。若出现这些情况，应恢复原代理设置，
不要简单扩大为无限制代理。不要为全系统配置这个端口。

### 接入方式 B：Clash/Mihomo 精确分流（可选）

参见 [示例配置](examples/clash-rules.yaml)。

1. 先备份自己的配置，再把本地 SOCKS5 出站和 UU 域名规则合并到原配置。
2. 把 UU 规则放在现有兜底规则之前。
3. 使用 **规则模式**。直连模式会跳过该规则；全局模式可能使用选中的远端节点。
4. 系统代理没有覆盖到的 UU 原生 socket 不一定会经过 Clash；不能仅凭模式判断成功。

示例不会添加 `MATCH,DIRECT`，以免覆盖你原有的其他软件路由。
原始排障阶段曾临时添加 `MATCH,DIRECT` 以保持校园网下非 UU 流量直连：
这会让其后的原有分流规则不可达，**不是适合直接分发给所有人的默认配置**。
回到必须依赖远端代理的个人网络时，务必恢复自己的路由策略。
另一个重要区别：UU 手动代理若直接指向 `17899`，该部分流量不经过 Clash；
只有“通过 Clash 规则分流”的部分才依赖 Clash 的规则模式。

## 验证

先检查客户端是否恢复服务连接，再实际连接自己拥有或获授权的设备：

1. 顶部服务器连接错误消失。
2. 在线设备状态刷新，而非仅看到缓存设备列表。
3. 能进入远程画面并进行正常操作。
4. 根据需要分别测试文件传输、断线重连、休眠恢复。

可选的基础测试（系统需有 curl）：

```bash
curl --noproxy '' --proxy socks5h://127.0.0.1:17899 \
  --connect-timeout 5 --max-time 10 -o /dev/null \
  -w 'HTTP=%{http_code} TLS=%{time_appconnect}\n' \
  https://api.nrd.nie.163.com/
```

根路径返回 404 也可证明完成了该次 TLS/HTTP 交互，但**不证明业务正常**。
不要使用 `-k` 跳过证书验证。

## 已知限制

详见 [验证记录与限制](docs/VALIDATION.md)。

- 默认端点映射只反映 2026-11-09 的单次排障，可能失效，不提供自动更新或自动切换。
- 改变 TLS record 并非对所有过滤方式有效；不支持跨多个 record 的 ClientHello 重组。
- TCP only，缺少 UDP、其他端口、IPv6 上游、HTTP 明文升级支持。
- 默认最多同时处理 48 个连接；长连接占满时其他请求可能等待。
- 本地无身份认证，其他本机进程/用户可以访问该端口，不适合不可信多用户主机。
- 只修复了连接路径，不修复 UU 账号、设备离线、服务端权限或 NAT 等其他问题。
- 不应把“当前可用”理解成“没有其他问题”或“可以无人值守长期使用”。

## 撤销

先恢复 UU 原来的代理选项，或者删除自己添加的 Clash 出站与对应域名规则；
再停止本程序。不要先停程序却让客户端继续指向这个端口。
不要覆盖与本项目无关的 DNS 修复、订阅、系统代理或其他分流规则。

此发布版没有安装器和自启项，也不会自动改写本机文件；本次实际排障留下的
本机专用管理脚本、备份和配置状态**不在这个仓库里**。
